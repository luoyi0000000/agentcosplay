### 修复过程中额外拦截的一项回归

调整并发建库顺序后，最初修正版在拒绝“未来 schema 版本”之前先修改了 journal_mode。这不是基线原有缺陷。主任务二次复核实际复现 `delete → wal`，补回归测试后增加了变更前版本检查，并保留事务内再次检查。现在拒绝未知新版本不会先改变该库的日志模式（`storage.py:59`）。

## 对真实中断的验证

新增测试启动独立 Python 子进程，在事务内改写已存在记录并新建记录，随后调用 `os._exit(17)`，故意跳过 finally/正常关闭。重新打开数据库后：原已提交记录保持原值，未提交新增记录不存在。

独立复核还跑了10轮×8个进程同时首次打开/写入同一新库，80次启动全部成功，每个库保留8条写入。单元测试保留10轮×8线程的多连接回归。没有把“没有报错”等同于“没有丢写入”。

### 旧库兼容与未验证项

旧版新建的 DB 可能是0644。新版在 POSIX 上会拒绝这种库，**不会删除数据，也不会自动 chmod**。若已有实际数据，先停止使用该库的所有服务，确认文件属主与路径，再把目标 DB 及存在的 `-wal/-shm` 收紧为0600，确认数据目录私有后重启。符号链接需使用真实受控路径。不要批量修改无关目录。

Windows 依赖账户/目录 ACL，尚未实机验证。文件 mode 检查不等于审计全部 ACL，也不防御已经能修改私有目录的同账号攻击者。手机端、真实远程 OAuth、宿主长期角色表现仍未验收。当前已复现缺陷已修复，不作“系统绝对没有漏洞”的保证。
